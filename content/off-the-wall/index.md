> 쉽게 말하면, Off the Wall은 내가 전에 한 지적을 줄이지 않고 그대로, 에이전트가 답하기 전에 다시 보여 주는 플러그인이다. 모델이 모르는 내 습관을 33번 시켰을 때 없으면 2번, 있으면 20번 따랐다(Claude Sonnet, 시험용으로 만든 습관). 뭘 하고 뭘 못 하는지는 [쉬운 설명 글](/otw-what-it-does/)에 따로 정리했다. 이 글은 그 전에 쓴 자세한 측정 기록이다.
>
> 업데이트 이력. 10월 29일에 큰 모델(Sonnet)에서도 같은 효과를 확인했고, 저장된 지적을 지우는 `otw forget`이 0.3.1에 들어갔다. 10월 28일에는 모델이 모르는 개인 선호에서 효과를 처음으로 쟀다(아래 7장). 10월 27일에는 입력 경계 수정이 0.2.0에 공개됐고 Codex 실제 호스트에서 한 번 돌려 본 기록을 추가했다. 10월 23일에는 과거 실험이 어디까지 말해 주는지 정리했다. 최신 숫자와 한계는 쉬운 설명 글에 있다.

코딩 에이전트를 고칠 때 중요한 건 "다음부터 잘해"라는 규칙만이 아니었다. 어떤 요청에서 무엇을 어떻게 고쳐 달랬는지가 다음 작업 앞에도 남아 있어야 했다.

[Off the Wall](https://github.com/toranalytics/off-the-wall)은 Claude Code와 Codex에 저장된 과거 정정 원문을 다음 요청의 컨텍스트로 인용하는 초기 플러그인이다. 더 나은 답변이나 비용 절감을 보장하는 도구는 아니다.

**[개인 기록 없이 원문 회수 데모 보기](/otw-recall-lab.html)**

데모는 설치나 로그인 없이 열린다. 입력은 전부 내가 만든 사례이고, 공개 훅이 실제로 돌려준 컨텍스트와 빈 저장소의 차이를 보여 준다. 좋아진 모델 답변을 꾸민 전후 비교가 아니다.

## 1. 원문이 돌아오는 순간

아래는 개인 대화에서 가져온 게 아니라 데모용으로 지어낸 사례다.

> 린트만 돌리고 "테스트 통과"라고 하지 마. 체크아웃 통합 테스트를 실행하고 실제 종료 코드를 보여줘.

나중에 "결제 핸들러 변경을 체크아웃 통합 테스트로 검증해줘"라는 새 요청을 보낸다. "검증을 잘하라"는 일반 문구 대신, 어떤 테스트와 어떤 증거를 요구했는지가 원문으로 컨텍스트에 돌아온다.

![합성 교정 입력과 실제 공개 훅의 컨텍스트 출력](recall-example.png)

*합성 입력을 격리해서 돌린 화면이다. 모델의 다음 답변은 실행하지 않았다. 다른 작업의 범위 지적도 같이 섞이는 한계가 있는데, 4장에서 얘기한다.*

데모에는 작업 범위를 지키는 사례, 선택을 맡겼을 때 다시 묻지 않는 사례, 무관한 요청에도 최근 교정이 들어오는 한계 사례가 있다. 핵심 세 사례의 정정은 최근 6개보다 오래된 항목이다.

## 2. 실제로 확인한 범위

공개 OTW 0.1.1의 고정 커밋 `07fe3d3d4f4accc153eb0684f506e0d3c206fdcc`를 수정하지 않고 실행했다.

- 합성 요청 4개 × 빈/저장 상태 × Claude/Codex 훅 모드, 합쳐서 CLI 훅 실행 16회.
- 저장된 교정과 요청은 내가 직접 만든 fixture다. 자동 판정이나 과거 기록에서의 추출을 검증한 게 아니다.
- 관련 있고 최근인 교정이 선택돼 `additionalContext`에 들어가는지, 미래 시점의 교정이 빠지는지 봤다.
- 개인 기록, 모델 제공자, 실제 Claude Code/Codex 세션은 쓰지 않았다.

회수됨, 모델이 따름, 실제 작업이 성공함, 사용자가 덜 고침은 서로 다른 단계다. 이 재현은 첫 번째까지만 확인했다.

### 2-1. 실제 Codex에서 한 번 돌려 본 기록 (10월 27일 추가)

위 재현은 호스트 없이 훅만 돌린 거였다. 그래서 macOS의 실제 Codex(codex-cli 0.162.1)에서 플러그인 0.2.0을 격리된 홈 디렉터리와 합성 프롬프트로 한 번 돌렸다. 플러그인 설치, 훅 신뢰, 한 턴의 교정 저장, 다음 턴에 그 교정이 개발자 메시지로 주입되는 것, 번들 예시 기록에 대한 `otw report`(답변 20개 중 9개 분류)를 확인했다. 기록은 [저장소 docs](https://github.com/toranalytics/off-the-wall/blob/main/docs/live-codex-smoke-2026-10-27.md)에 있다.

- 훅은 신뢰하기 전에는 돌지 않는다. 설치만 하면 조용히 아무 일도 안 일어난다. `/hooks`에서 신뢰해야 하고, 0.2.1부터 `otw status`가 최근 훅 활동과 신뢰된 항목 수를 보여 준다.
- 한 대의 컴퓨터에서 한 번 돌린 것이다. 모델이 회수된 교정을 따랐는지는 보지 않았다.
- Claude Code는 대화형으로 돌려 보지 못했다. 처음에는 로그인된 Claude Code가 없어서 못 했고, 나중에 Claude Code 2.1.311의 헤드리스 모드에서 플러그인 0.2.1로 교정 저장과 새 세션의 회수를 한 번 확인했다. 다만 같은 시험의 셋째 턴에서 모델이 6분 동안 비정상적으로 긴 출력을 낸 적이 한 번 있었고(8회 재시험에서는 재현되지 않았다), 대화형 사용은 확인하지 못했다. 기록은 [저장소 docs](https://github.com/toranalytics/off-the-wall/blob/main/docs/live-claude-smoke-2026-10-27.md)에 있다.

## 3. 지금 공개판이 하는 일

처음 공개했을 때는 저장된 교정 중 과거 요청과 문자열 특징이 비슷한 최대 3개를 먼저 고르고 최근 항목으로 채워서 최대 6개를 인용했다. 0.3.0부터는 `recallWide`가 기본으로 켜져 있어서, 20자 이상 요청에는 비슷한 정도 순으로 최대 6개를 붙이고 겹치는 게 전혀 없는 건 뺀다. 검색은 단어와 글자 2개 단위(bigram) 기반 TF-IDF라서, 뜻을 이해하거나 적용 범위를 정확히 판단한다고 보장하지 않는다.

판정 기능을 켜면 직전 답변과 새 메시지를 별도 프로세스에서 검토해 교정 후보를 저장한다. `report`는 기존 대화 기록에서 교정을 분류하는 선택 진단 기능이다. 모델 선택 안내도 들어 있지만 자동 최적화나 일반적인 비용 절감이라고 소개하지 않는다.

인용 블록은 대화창에 카드로 뜨는 게 아니라 모델에게 전달되는 추가 컨텍스트다. 이 글의 데모는 그 숨은 입력을 들여다보는 별도의 검사 화면이다.

## 4. 원문만 보존해서는 부족하다

데모의 결제 테스트 요청에는 "로그인 파일만 고쳐라" 같은 다른 작업의 일회성 범위 교정도 같이 뽑혔다. 무관한 화성 질문에서도 최근 교정 6개가 들어왔다.

핵심 문장이 들어왔다고 선택 전체가 적절하다고 할 수는 없다. 원문의 "이번 요청"이 과거 작업을 가리키는지, 지금도 유지해야 할 선호인지 구분해야 한다. 모델이 이 때문에 실제로 잘못 행동했다는 결과는 아직 재 보지 않았다.

다음에 검토할 과제는 지속적인 선호와 일회성 작업 지시의 구분, 원래 요청·프로젝트·적용 범위의 출처 표시, 무관한 최근 항목 처리다. 아직 공개 기능으로 구현됐다는 뜻은 아니다.

사용자 역할의 자동 플러그인 메시지가 사람 교정처럼 분류될 수 있는 입력 경계 문제도 확인했다. 출처 태그와 작업 디렉터리 기준 회수를 넣은 수정이 0.2.0으로 공개됐다. 그래도 자동 입력을 완전히 가려낸다고 보장할 수는 없다. 이전에 내가 SNS에 올렸던 개인 기록 집계(수천 건 중 가장 많은 교정 횟수, 비율 등)는 이 문제가 섞였을 수 있어서 철회했고, 다시 확인하기 전에는 쓰지 않는다.

## 5. 과거 실험은 어디까지 말해 주나

예전에 한 사람의 기록에서 고른 요청 39개를 도구 없이 텍스트로 다시 돌리고 모델이 채점하는 탐색 실험을 보고했다. 원문 6개와 지적 예측 지시를 같이 붙인 조건이 아무것도 안 붙인 조건 대비 25승 11무 3패로 집계됐다.

하지만 무작위 규칙과 직접 비교한 17승 14무 8패는 확실한 우위의 근거가 아니다(보고된 양측 검정 p≈0.11). 원문 형식과 예측 지시를 분리하지도 않았으니 원문 하나의 인과효과라고 할 수 없다.

보존된 과거 실행 로그에서 집계와 조건은 확인했지만 원본 case별 산출물을 독립적으로 다시 돌린 건 아니다. 실행이나 사실 확인이 필요한 업무 대부분은 이런 텍스트 재생으로 평가할 수 없다. 지금 공개 버전의 실제 작업 성공률, 장기 유지, 평균 비용 절감은 따로 검증해야 한다.

## 6. 데이터와 비용

저장된 결과와 세션 상태의 기본 위치는 로컬 `~/.otw`다. 다만 판정과 개인 리포트 분석은 내가 쓰는 Claude/Codex CLI를 통해 대화 발췌문을 해당 모델 제공자로 보낸다. "어떤 데이터도 컴퓨터 밖으로 나가지 않는다"는 설명은 맞지 않다. 별도 API 키가 필요 없어도 제공자 호출은 플랜 한도, 사용량, 요금을 쓸 수 있다.

회수 블록이 프롬프트를 얼마나 늘리는지도 한 번 재 봤다(Codex 0.162.1, 합성 교정 6개, `codex exec resume`의 두 번째 턴). 회수 기능을 끄면 입력 13,743토큰, 회수만 켜면 14,028(+285), 서브에이전트 모델 선택 안내만 켜면 14,364(+621), 둘 다 켜면 14,781(+1,038)이었다. 조건당 한 번씩이라 참고용이다. 재개한 세션에서 모델 선택 안내가 두 번 주입되는 것도 봤는데, 이 중복은 0.2.2에서 고쳤다(재개 시험 추가). 이 측정은 프롬프트 크기만 본 거라 답변 품질이나 비용 절감을 뜻하지 않는다. 기록은 [측정 메모](https://github.com/toranalytics/off-the-wall/blob/main/docs/token-overhead-2026-10-27.md)에 있다. 판정은 분리된 프로세스로 돌지만 전체 사용 경험에 지연이 없다고 보장하지는 않는다. 저장소 삭제와 제공자 쪽 데이터 처리는 별개다.

## 7. 10월 28일 측정: 모델이 모르던 내 습관을 따르나

앞선 시험은 모델이 원래 잘하는 실수(테스트 돌리기, 끝까지 하기)를 골라서 켜도 꺼도 만점이었다. OTW가 쓸모 있어야 하는 곳은 거기가 아니라 모델이 알 수 없는 개인 습관이다. 커밋 형식, 쓰는 패키지 도구, 말투, 날짜 형식 같은 것들이다.

그래서 이런 선호 11개를 작업으로 만들어 각각 3번씩 33번 시켰다. 작업과 채점기는 내가 아닌 다른 모델이 썼고 전부 자동 채점이다. 계획은 실행 전에 고정했다.

| 조건 | 습관을 지킨 횟수 |
|---|---|
| OTW 없음 | 1/33 |
| OTW 기존 기본(좁게 찾기) | 9/33 |
| OTW 넓게 찾기(`recallWide`, 0.3.0부터 기본) | 17/33 |

- 저장소를 바꿔 다시 했는데 비슷한 크기의 격차가 나왔다(16/33 대 8/33, 17/33 대 9/33).
- 원인은 검색이다. 맞는 과거 지적이 인용에 들어오면 모델이 훨씬 자주 따르고, 못 찾으면 달라지는 게 없다. 넓게 찾기가 더 자주 찾는다.
- 한계도 분명하다. 작업 11개 중 1개는 "한 문장" 형식이 너무 엄격해서 인용이 보여도 안 따랐다. 0/3이던 다른 작업 하나는 나중에 발견한 채점기 오류(코드 블록으로 감싼 답을 탈락시킴)였고, 기록을 다시 읽으니 교정을 본 6번 중 5번이 따랐다(사후 재집계라 표의 수치는 원래 값 그대로이고, 실제 효과를 적게 보여 준다). 모델이 원래 잘하는 실수에서는 이점을 못 찾았고(16개 중 14개 작업), 규칙 150줄을 그냥 넣은 쪽이 전체로는 더 높았다. 다만 기록이 길어지면 규칙 전체를 넣는 방식은 못 쓴다.
- 채점기 오류를 고친 뒤 같은 저장소와 작업으로 한 번 더 돌렸다(99회). 회수 없음 2/33, 기존 기본 14/33, 넓게 찾기 25/33이다. 방향은 같은데 숫자가 높아진 건 일부는 오류 수정, 일부는 실행마다 달라지는 변동 때문이라 위 표는 바꾸지 않았다. 기록은 [저장소 docs](https://github.com/toranalytics/off-the-wall/blob/main/docs/preference-experiment-2026-10-28.md)에 있다.
- 아직 모르는 것은 실제 사용자의 긴 기록, haiku와 Sonnet 말고 다른 모델(Opus, Codex 모델), 대화형 사용, 장기 효과다. (10월 29일에 Sonnet으로도 같은 작업을 돌려 회수 없음 2/33, 현재 기본 20/33을 얻었다.) 이 지적들은 모델이 쓴 합성 기록이다. 넓게 찾기는 모든 요청에 인용 최대 6개(약 300토큰)를 붙이는 대가가 있어서, 선호와 무관한 작업 14개에서 방해가 되는지도 따로 확인했다(OTW 없음 40/42, 넓게 찾기 41/42, 방해 없음 확인. 출력 토큰은 약 9% 늘었다). 그래서 0.3.0부터 기본값으로 켰고, 20자 미만의 짧은 입력은 기존 기준을 쓴다(이 보호 장치 자체는 시험하지 않았다). 끄려면 설정에 `"recallWide": false`를 넣으면 된다.

실험 기록, 계획, 스크립트, 독립 검토에서 나온 약점까지 [저장소 docs](https://github.com/toranalytics/off-the-wall/tree/main/docs)에 있다.

## 8. 써 보기 전에

먼저 [합성 원문 회수 데모](/otw-recall-lab.html)를 보면 좋겠다. 실제 개인 기록 분석과 회상 저장은 별도로 고르는 기능이다. 입력 경계 수정은 공개됐지만 실제 사용으로 충분히 검증되지는 않았다. 그래서 이 글은 개인 기록에 `report --seed`를 돌리는 걸 아직 권하지 않는다.

설치와 설정은 [현재 README](https://github.com/toranalytics/off-the-wall)를 보면 된다. Codex는 `/hooks`에서 훅을 신뢰하는 단계가 필요하고, 안 하면 훅이 조용히 돌지 않는다(`otw status`로 확인할 수 있다). Windows는 CI의 테스트와 훅 실행이 성공한 것과 실제 호스트 세션이 성공한 것을 구분해야 한다.

가장 필요한 피드백은 성공담만이 아니다. 관련 없는 교정이 돌아왔는지, 필요한 교정이 빠졌는지, 회수된 뒤에도 같은 실수를 했는지를 알고 싶다. 원문, 코드, 회사 이름 없이 [이슈](https://github.com/toranalytics/off-the-wall/issues)로 알려 줘도 된다. 개인 기록이나 리포트 원문을 내라고 하지 않는다.
